# Prometheus 生命周期简化：第一步盘点与改造顺序

日期：2026-09-10。状态：第一步只读盘点已完成，本文不是功能已实现声明。

## 已确认的产品目标

操作简单、能力完整。面向 Prometheus 监控整体生命周期，兼顾新建与存量环境、旧版本、参数差异、离线与失败恢复。常用路径只填写必要信息，高级能力保留；平台负责关联资源、推荐值、检查和执行证据。用户要求一步一步推进。

保留单平台进程、SQLite 和现有受管生命周期设计。Linux binary/systemd 是当前正式路径；Windows、旧 Docker/WSL 等按实际能力与验收证据单独标明，不因代码存在便宣称全平台支持。此前用户明确不要求 HTTPS，本轮不重新引入该交付要求。

## 有代码依据的优先缺口

### P0：未知版本可能获得通过结论

api/handlers/deployment_preflight.go 的 thanosSupportsPrometheus 解析异常返回或保留 0，并以 prometheusMajor < 3 等条件决定兼容。格式不合法不能等同于“已知较旧版本”。现有 TestThanosPrometheusVersionCompatibility 覆盖正常版本组合，需补非法、空、预发布、构建信息和未知版本用例。

第一批要求：严格解析；已知不兼容阻断；未知单独表达并说明缺少的证据。发现/观察未知服务仍允许保留，但涉及托管写入时必须满足该动作需要的证据，不能简单让所有未知情况均通过或全部禁用。

### P0：计划内依赖不能证明版本组合兼容

同文件 preflightDependencies 对已运行 Thanos→Prometheus 依赖有专项判断；计划分支主要依据 PlannedComponents 中的组件类型和顺序放行，不能证明计划的两种版本兼容。反向操作（升级 Prometheus 时影响既有 Thanos）也需要核查并纳入统一规则。

第一批要求：解析“执行后的有效拓扑”，版本来自实际组件或本次计划；保留明确实例 ID，不能在同机多实例中随意 First 选中依赖。缺失版本/实例必须返回具体补充项。

### P0：升级风险等级不等于迁移可行性

services/change_service.go 的 preflightUpgrade 已检查健康、版本/包、冲突及空间，结尾以主版本是否变化给出风险；没有在该路径发现 Prometheus 2→3 中间版本、旧采集协议和产品迁移规则的统一表达。现有恢复机制应继续复用，不能误报“没有备份恢复”。

第一批要求：升级与降级分开判断，输出直接执行/需中间版本/需恢复配套数据/已知不支持/证据不足。新旧参数和配置验证必须发生在停旧服务之前；已知阻断不能仅转成一个可忽略警告。

### P1：参数定义尚未表达版本适用性

DeploymentParameter 没有版本范围、弃用/替代参数和证据字段；applyPrometheusDeploymentArgs 主要按固定映射生成参数。不能据此认定每个参数都存在兼容缺陷，但无法用这份定义证明所有目录版本都适用。

第一批要求：常用参数按目标版本解析。识别有效值来源（现有值/用户填写/推荐值），默认值仅补缺失；保留无法无损映射的高级原始配置，并清楚显示冲突。版本切换后重新预检，旧预检结果不能继续使用。

### P1：运行环境证明不够统一

validateExtractedBinary 当前仅对 Loki/Promtail 在平台侧运行版本命令。该检查不能证明远程目标架构、动态链接库或全部组件可运行；部分组件还有安装后的校验，应保留但不能把它当成完整的部署前兼容证明。

后续要求：主机只读信息与包格式/架构元数据先比对；若需上传并执行候选程序，作为明确的准备任务执行，不能偷偷改变“只读预检”的约定。探测失败说明原因，不把平台机器探测结果用于远程机器。

## 场景矩阵与验收要求

| 场景 | 用户看到的简化流程 | 必须保留的判断/证据 |
|---|---|---|
| 全新单机 | 选推荐方案→预览→部署 | 资源、端口、包、配置、组件就绪、目标有数据 |
| 多台 Linux 批量接入 | 填表→选监控方案→执行 | 每台连接/归属/Exporter/采集结果，成功行不重复执行 |
| 已有完整监控 | 发现→观察或托管 | 真实版本、路径、服务名、参数；观察不修改 |
| 已有部分组件 | 补齐缺失项 | 按明确实例关联依赖，不覆盖已有服务 |
| 同机多实例 | 选实例 | PID、unit、地址、配置/数据路径共同识别 |
| 没有管理权限的目标 | 仅采集接入 | 不承诺安装、启停、升级或卸载能力 |
| 老 Prometheus 2.x | 识别当前能力 | 不注入仅新版本适用的字段；目标版本校验 |
| Prometheus 2→3 | 展示分阶段升级方案 | 中间版本、采集协议、规则语义与恢复条件 |
| 版本未知/自编译 | 显示未知及补充方法 | 不猜成 0，也不冒充已验证版本 |
| Thanos 组合/计划依赖 | 自动校验所选组合 | 新建依赖、既有依赖、反向升级都校验 |
| Grafana 跨迁移升级 | 展示影响和恢复点 | 数据库、配置、密钥、provisioning、插件匹配 |
| Linux 不同架构/旧系统 | 显示匹配包或具体缺口 | 架构、glibc/加载器、systemd、权限；不盲选 amd64 |
| Windows | 分别展示采集/发现/托管能力 | 版本/服务名/路径/WinRM；MSI 实机未验收明确标识 |
| 离线/代理环境 | 选已入库包 | 校验和、匹配工具、版本数据更新时间，离线不强制联网 |
| 自定义目录/参数 | 继承现有设置 | 路径归属、有效参数、显式 Diff，避免悄悄覆盖 |
| 数据盘空间紧张 | 展示资源建议 | 同盘其它服务、WAL、压缩临时空间、备份空间 |
| 通知接入 | 配渠道→测试→查看结果 | 配置发布、平台直发、Alertmanager 路由、真实收件分开 |
| 连接中断/平台重启 | 保留进度并核对 | 未知不显示失败后直接重试，操作锁和恢复证据 |
| 升级失败/降级 | 按恢复点恢复 | 程序+配置+数据配套，恢复失败保持明确阻断 |
| 退役 | 选停止监控/解除托管/卸载 | 三种意图区分；采集清理、服务验证、数据默认保留 |

## 最佳实践的官方依据与采用方式

核对日期 2026-09-10；latest 文档会变化，落地规则必须固定来源版本、适用范围、核对日期和测试证据，不能只保存一个布尔 compatible。

1. Prometheus 官方 3.0 发布说明建议先升级至 2.55，再升级到 3.0，并描述回退到 2.55 的边界。此依据不能推广为所有未来 3.x 均可任意回退。来源：https://prometheus.io/blog/2024/11/14/prometheus-3-0/
2. Prometheus 3 的 Content-Type 处理更严格，旧端点可能停止被采集；按端点证据选择修复协议或版本适用的 fallback，而非全局静默放宽。来源：https://prometheus.io/docs/prometheus/latest/migration/
3. Prometheus 官方建议保留大小至多使用所分配磁盘的约 80–85%，为压缩等留余量；平台建议采用用户为该实例分配的预算，不能简单取共享磁盘总容量的 85%。同时设置时间/容量时，先达到的条件生效；NFS 不应当作受支持的本地 TSDB 存储。来源：https://prometheus.io/docs/prometheus/latest/storage/
4. Grafana 13 的统一存储迁移使直接降级读到旧表而非新数据；回退应恢复升级前数据库。插件、配置及密钥也需匹配。来源：https://grafana.com/docs/grafana/latest/upgrade-guide/upgrade-v13.0/

## 实施路线与取舍

比较三种方案：仅合并菜单最快，但版本判断问题仍存在；整体重写容易丢失已有恢复/权限能力且回归面大；推荐复用现有服务，先统一预检依据，再逐步收拢操作入口。

1. **第一步（本文）**：场景、关键缺口与证据盘点。
2. **第二步**：先修严格版本解析与兼容性结果表达；从现有 Thanos/Prometheus 规则切入，以最小边界测试证明未知不误放行，不扩大为任意旧版本全部支持。
3. **第三步**：补计划内依赖版本/实例绑定与反向升级检查；共享结果供预检、计划与执行使用，绑定预检快照防止执行前环境变化。
4. **第四步**：版本适用参数、产品迁移规则、匹配校验工具和升级前兼容检查；按组件逐个验证。
5. **第五步**：统一“搭建→批量接入→运行验收”入口；表单简化但支持高级参数，检查分阶段而非一个含糊成功标记。
6. **第六步**：统一维护、恢复、退役入口，并补相关失败/中断场景。

每一步的完成条件：相关回归测试、有效/无效输入、明确的未知状态、无新增敏感信息暴露；涉及业务符号先做 GitNexus impact，提交前做 detect_changes。远程写入验收使用隔离环境；生产升级与本次开发分开执行。
