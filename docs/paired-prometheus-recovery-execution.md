# Prometheus 成对历史恢复操作说明

成对恢复将同一恢复点的 Prometheus 程序、启动文件、配置和完整数据一起恢复。恢复会停止所选实例。只有程序身份、实际启动参数、监听进程和就绪检查通过，并且结果写入数据库后，才报告成功。

## 日常操作

1. 为 binary/systemd Prometheus 创建升级变更时，可勾选“升级前创建历史恢复点”。它会额外停止、采集并恢复当前实例，同时保留原有普通自动回滚备份；需要额外停机时间和磁盘空间。未选择时保持原升级流程，已选择但采集失败时不会继续升级。
2. 在维护或组件变更记录中打开对应升级计划，选择“恢复升级前历史状态”查看预览，核对组件、当前版本和历史版本。以预览结果为准，存在备份记录不等于该恢复点可用。
3. 确认后执行恢复。系统先保存当前检查点，再恢复历史匹配文件并验证实例。不要在执行过程中发起同实例的配置、升级或退役操作。
4. 查看最终结果；连接中断时先刷新事务状态，不能通过重复提交来判断结果。

读取接口为 `GET /api/v1/change-plans/:id/paired-recovery`；执行接口为 `POST /api/v1/change-plans/:id/paired-recovery`。读取遵循平台读取权限，执行要求 `change_admin` 或 `system_admin`。响应只公开预览与事务状态，不提供私有启动文件、命令或凭据。

配置、普通备份和退役继续使用已有入口。退役需区分保留服务、卸载但保留数据和完整删除；默认保留数据。

## 结果的含义

- `restore_completed`：历史实例已恢复并通过校验；组件记录更新为历史版本和历史镜像，变更计划标记为已回滚。
- `restore_compensated`：请求的历史恢复失败，操作前的实例和数据已恢复并通过校验。它不表示历史恢复成功。
- 其他未结束阶段：恢复尚未完成或需要人工处理。平台保留操作隔离；不要把超时当作成功，也不要反复执行请求。

界面超时或断开后，应先刷新事务结果。重复提交不会重放已有恢复；正在执行或中断的事务需要检查其持久状态。

## 中断后的执行恢复

先停止使用同一数据库的平台进程，再运行与数据库版本匹配的服务程序：

```sh
./server --data-dir=/var/lib/promlifecycle \
  --recover-prometheus-restore-execution=123 \
  --restore-backup-root=/backups
```

将 `123` 替换为恢复事务 ID；数据目录和备份根目录必须使用原配置。数据库为 `<data-dir>/promlifecycle.db`，备份根目录参数默认 `/backups`。正常服务通过环境变量 `BACKUP_ROOT` 设置自定义备份根目录时，恢复命令须显式传入同一路径。该命令取得与正常启动相同的独占数据库锁，校验并接管已开始执行的恢复，目标是恢复到操作前检查点。它不会启动 HTTP 服务、调度器或业务迁移。成功输出公开事务。接管未结束的执行后，结果为补偿完成；对于已经结束的事务，仅返回已有结果，不再次执行。

尚未开始执行的暂存中断仍使用既有 `--recover-prometheus-restore-stage` 命令。更早的检查点中断不属于执行恢复命令的支持范围。校验失败、无法确认远端操作已结束或补偿失败时，会保留隔离和已有文件，不能靠删除事务或锁记录继续操作。

## 支持范围与存储

当前路径用于已通过预检的 Linux binary/systemd Prometheus 实例。就绪检查固定到所选进程拥有的本地监听连接，并保留请求主机名和路径；默认双栈监听可使用经核验的 IPv6 回环地址。测试机使用 curl 7.61.1；运行环境需要支持 `--connect-to`，非回环 IPv4 校验还需要 `ip -4 route get`。

恢复会保留历史恢复点、当前检查点、暂存副本和被替换目录，需预留额外磁盘空间。本轮不自动清理这些保留目录；未完成事务的证据不能删除。历史数据恢复成功意味着回到所选时间点，其后的数据不属于该历史结果。

## 已验证范围

本地文件测试覆盖不同历史/当前程序与数据、失败补偿、事务提交失败、并发和中断接管，并包含监听归属、代理绕行、默认双栈以及本机地址校验。

在两台受控测试主机的独立 systemd 实例，已分别验证历史固定样本恢复和注入历史启动失败后当前样本恢复；临时资源清理完成，原有 9090/9100 业务正常。本次真实快照两侧均使用 Prometheus 2.55.0，因此不把它算作跨版本迁移验收。
